## TL;DR

Two independent, well-documented technical domains, both organized around the same core idea — **chain of trust rooted in immutable/OTP hardware, extended by cryptographic signatures at every stage**. Raspberry Pi's secure boot is a maturing, officially documented (if fiddly) embedded chain-of-trust with real vendor docs, real tooling, and real hardware-security research (RP2350 hacking challenge). Satellite protocol security is a fast-moving, standards-driven field (CCSDS SDLS/CFDP + NASA/NIST/CISA frameworks) with a 2025-2026 wave of academic work explicitly closing the "these protocols were designed trusted, not secured" gap — including a paper that literally benchmarks a Raspberry Pi 4 as a CubeSat security testbed, bridging both of your topics.

**Round 2 update:** the two domains have a much more direct bridge than the Pi-4-as-CubeSat-testbed coincidence above — [Space Fabric: A Satellite-Enhanced Trusted Execution Architecture](https://arxiv.org/abs/2603.23745) (Rezabek/Malkhi/Yahalom, Mar 2026) literally combines an embedded chain-of-trust (NXP i.MX6UL HAB — structurally the same OTP-fused-hash pattern as Raspberry Pi secure boot, just on different silicon) with satellite protocol security (a new ground-station attestation protocol, SEAP), because that's exactly what a satellite-native TEE needs. Independent 2026 literature confirms the gap Space Fabric claims to close is real: no CCSDS/NASA/NIST standard addresses proving code executed *on a specific satellite* rather than a ground-based clone, and on-orbit cryptographic key *generation* (not just rotation) appears to have no precedent before this paper. Separately, the RP2350 hacking-challenge results this brief flagged as pending have since concluded publicly (39C3 talk, Dec 2025) — real, verifiable material this brief was missing.

## Part A — Raspberry Pi Secure Boot: Deep Technical Sources

### How the chain actually works (synthesized from official + technical sources)

1. **BootROM (immutable, masked in silicon)** verifies the signature of the first mutable stage using a public key baked into the SoC.
2. **EEPROM bootloader (`bootcode`/`bootmain`/`recovery.bin`, via `rpi-eeprom`)** — its public key hash is fused into **One-Time-Programmable (OTP)** memory (`program_pubkey=1`). Once fused, the BootROM will only execute EEPROM images signed with the matching private key.
3. **`boot.img` / BL3 (often U-Boot)** is signed with a *customer* key, verified by the trusted EEPROM stage before execution; on Pi 4 the Device Tree Blobs live in the bootloader partition and must be authenticated before U-Boot runs (they aren't inside the FIT image, unlike most other embedded targets).
4. **Lockdown**: `revoke_devkey=1` blocks rollback to pre-secure-boot EEPROM releases (mandatory for production), and `program_jtag_lock=1` disables VideoCore JTAG — but only after `program_pubkey` + `revoke_devkey` are set and the device is fully tested, since it kills failure-analysis access permanently.

### Evidence by Surface

- **Raspberry Pi official docs — `config_txt` Secure Boot properties** — primary source for `program_pubkey`, `revoke_devkey`, `program_rpiboot_gpio`, `program_jtag_lock`; explicitly states secure boot targets **buildroot-based images, not Raspberry Pi OS** (unsupported combination people keep trying). `strong` — https://www.raspberrypi.com/documentation/computers/config_txt.html#secure-boot
- **`raspberrypi/usbboot` — `docs/secure-boot.md`** — official low-level walkthrough of enabling secure-boot via the `rpiboot` provisioning tool. `strong` (official repo) — https://github.com/raspberrypi/usbboot/blob/master/docs/secure-boot.md
- **`raspberrypi/rpi-sb-provisioner` issue #246** — real-world operational cost: secure boot roughly **doubles boot time (~17-18s added)** on provisioned boards — a concrete, current trade-off missing from most tutorials. `moderate` (maintainer-confirmed issue, Dec 2025) — https://github.com/raspberrypi/rpi-sb-provisioner/issues/246
- **The Embedded Kit — "Raspberry Pi: secure boot enablement"** (Feb 2026) — the best deep, step-by-step technical article found: full BootROM → `bootsys` → `bootmain` → BL3 flow, plus the 3-phase practical recipe (sign `boot.img`/`boot.sig` → configure & sign BL2 `boot.conf` with `SIGNED_BOOT=1` via `rpi-eeprom-config` → fuse OTP via a GPIO-forced `RPIBOOT` mode). Written by an embedded engineer shipping a Yocto-based secure image (Welma). `strong` — https://theembeddedkit.io/blog/raspberry-pi-secure-boot-enablement/
- **Raspberry Pi Forums — "Ensure EEPROM Full Overwrite and Eliminate Persistent Malicious..."** — community-surfaced nuance: the BootROM enforces signed EEPROM firmware, but incomplete-erase edge cases can leave stale/malicious EEPROM remnants; worth reading before assuming "signed = clean." `moderate` (forum, Jan 2026) — https://forums.raspberrypi.com/viewtopic.php?t=395642
- **Circuit Cellar — "Exploring the RP2350 Security"** (Colin O'Flynn, hardware security researcher) — covers the *next-generation* silicon story: RP2350's boot ROM, OTP-based secure boot, a **Redundancy Coprocessor (RCP)** for control-flow/glitch protection, and Raspberry Pi's own public **hacking challenge** where researchers (incl. ChipWhisperer/IOActive-adjacent teams) tried to break it via fault injection and side channels — a rare "security through transparency" stance for a sub-$1 MCU. Full text is paywalled; abstract/topic list confirmed. `moderate` — https://circuitcellar.com/research-design-hub/design-solutions/exploring-the-rp2350-security/
- **Security StackExchange — "(How) is a TPM added to a Raspberry Pi 5 secure?"** — clarifies that Pi 5's OTP-fused public key + BootROM verification *is* the root of trust, and that a bolted-on TPM only helps if the boot chain up to the TPM is itself already trusted. Good mental-model correction. `moderate` — https://security.stackexchange.com/questions/282129/how-is-a-tpm-added-to-a-raspberry-pi-5-secure
- **arXiv 2601.07402 — "Peacock: UEFI Firmware Runtime Observability..."** — not Pi-specific, but directly relevant context: catalogs how BlackLotus, LOGOFAIL, and PIXIFAIL bypassed *signed* UEFI secure boot chains — the same class of "signed but exploitable" risk that applies once a Pi-based product ships a vulnerable-but-signed U-Boot/BL3. Useful for threat-modeling the "what if my signed bootloader has a bug" case. `moderate` — https://arxiv.org/pdf/2601.07402

### Deep Dive — RP2350 Hacking Challenge results (resolves the "paywalled, unverified" gap above)

The Circuit Cellar item above was paywalled past the abstract; this round found and independently verified (via `media.ccc.de`) the primary account of what that hacking challenge actually found:

- **All 5 winning attacks now have a public technical deep dive** — [39C3 talk, "Of Boot Vectors and Double Glitches: Bypassing RP2350's Secure Boot"](https://media.ccc.de/v/39c3-of-boot-vectors-and-double-glitches-bypassing-rp2350-s-secure-boot) (stacksmashing & nsr, recorded/published 2025-12-27, CC-BY-4.0). Confirmed content matches the description: fault injection forcing an **unverified vector boot** (complete secure-boot bypass), a **double-glitch** attack for direct OTP secret readout, plus laser fault-injection and reset-glitch variants from other researchers — despite RP2350 shipping active anti-glitch hardware (glitch detectors, a Redundancy Coprocessor). `strong`, independently verified.
- **Raspberry Pi shipped a fix and ran a second round.** The [A4 silicon stepping](https://www.hackster.io/news/raspberry-pi-squashes-security-bugs-fixes-e9-erratum-with-the-rp2350-a4-stepping-cff097536171) is a drop-in replacement that patches the glitching vulnerabilities from round 1, fixes the unrelated E9 GPIO erratum, and adds a hardened AES/self-decrypting-binary SDK feature — which immediately became the target of a **second RP2350 Hacking Challenge**, run with researcher Thomas Roth and Hextree, specifically probing that new AES feature's side-channel resistance. `moderate-strong` (direct quote of Raspberry Pi's own announcement via Hackster.io), not independently re-verified against the primary RPi blog post.
- Net effect on this brief: RP2350's break class (voltage/laser/reset fault injection against physical silicon) is a fundamentally different threat model than the i.MX6UL HAB break found below (a certificate-parsing logic bug) — worth keeping distinct when comparing "which chain of trust is more attackable."

### Deep Dive — i.MX6UL HAB: the *other* embedded secure-boot Space Fabric actually uses

Space Fabric (see cross-domain section below) runs on **NXP i.MX6UL** (USB Armory Mk II / MCIMX6ULL-EVK), not a Raspberry Pi. Its secure-boot mechanism, **HAB (High Assurance Boot)**, is structurally close enough to Pi's scheme to treat as the same pattern family, with real differences:

- **Same OTP-fused-hash pattern**, but with **4 co-equal SRK (Storage Root Key) public keys** hashed together and fused into OTP (`OCOTP_SRK0`-`SRK7`), vs. Pi's single `program_pubkey`. Each of the first 3 SRKs is **individually and permanently revocable** on a per-unit basis (`OCOTP_SRK_REVOKE`) — a richer per-key rollback model than Pi's single `revoke_devkey` toggle. `strong` — primary source: [usbarmory/usbarmory wiki, "Secure boot (Mk II)"](https://github.com/usbarmory/usbarmory/wiki/Secure-boot-\(Mk-II\)) (maintained by the GoTEE/USB-Armory project itself).
- **Richer JTAG lockdown**: 4 independent fuses (`SJC_DISABLE`, `JTAG_SMODE`, `JTAG_HEO`, `KTE`) vs. Pi's single `program_jtag_lock` — HAB even fuses off its *own* runtime ability to re-enable JTAG (`JTAG_HEO`), closing a re-enable path Pi's simpler model doesn't need to separately address.
- **Known, independently-verified CVE**: [CVE-2017-7932 / CVE-2017-7936](https://nvd.nist.gov/vuln/detail/CVE-2017-7932) — "improper certificate validation... possible to bypass signature verification by using a specially crafted certificate leading to execution of an unsigned image," affecting the whole i.MX6/Vybrid family incl. i.MX6UL(L). CVSSv3 6.0 MEDIUM, fixed in silicon revision 1.2+. **Verified directly against NVD** (not just the secondary usbarmory-wiki citation) — this is a real, confirmed logic bypass, structurally different from RP2350's fault-injection breaks (parsing bug vs. physical glitch). `strong`, independently verified against NVD.
- **GoTEE (the TamaGo/Go TrustZone framework Space Fabric's paper mentions) adds no boot-time verification of its own** — it's a pure runtime isolation framework launched as an ordinary HAB-signed image; all of the *runtime* attestation logic in Space Fabric (measuring loaded Trusted Applets, issuing signed evidence) lives in OP-TEE's Attestation PTA, not in HAB or GoTEE. `strong` — cross-confirmed from GoTEE's own README plus the Space Fabric paper's text (see next section for the one internal inconsistency worth flagging).

## Part B — Satellite Protocol Security: Best Practices

### The standards layer (what "secure" means for CCSDS)

- **CCSDS Security Core Suite** splits security into three layers: **Link** (Space Data Link Security Protocol — SDLS, CCSDS 355.0-B-2), **Network**, and **Application** (e.g., securing CFDP file transfers). The Green Book (CCSDS 350.0-G-3, "The Application of Security to CCSDS Protocols") is the rationale document; the Blue Books are the binding recommended standards.
- **SDLS (CCSDS 355.0-B-2)** generalizes link-layer confidentiality, integrity, and anti-replay to TM/TC/AOS transfer frames — it's optional-but-standardized, meaning a huge number of missions still fly it *unencrypted* unless explicitly turned on.
- **CFDP (CCSDS 727.0-B-5)** — the file-transfer workhorse for deep space/CubeSats — was **designed for a trusted, error-free environment**: no confidentiality, no authenticated headers, no replay protection by default. This is the single most concrete, exploitable gap identified across the 2025-2026 literature.

### Evidence by Surface

- **CCSDS.org — official Blue Book/Green Book publications** (SLS area) — primary standards source for SDLS, CFDP, TM/TC frame formats. `strong` — https://ccsds.org/view/sls/ , https://ccsds.org/publications/allpubs/
- **NASA SPARTA — "Space Security: Best Practices Guide (BPG)"** — NASA's mission-security control catalog, mapped to 14 principles across space-vehicle and ground segments (data-flow mapping, least privilege on shared buses, boundary protection between ground↔space with encryption + GCM authentication, comprehensive auth/authz, communications/PNT jamming-and-spoofing survivability, software assurance + supply-chain integrity, malware protection, on-board adversarial-action detection, fault-management bypass protection, mission recovery, cyber-safe state). Cross-mapped to NIST SP 800-53, ISO 27001, and MITRE D3FEND. This is the single best **actionable checklist** found. `strong` — https://sparta.aerospace.org/countermeasures/nasabpg
- **"Design of a resilient multi-layered security framework for satellite communications"** (Int. J. Information Security, Springer, open access, Feb 2026) — directly integrates AES-GCM + ECC (ECDH/ECDSA) into CFDP, adds GPS-disciplined time sync for replay protection and dual-band UHF/S-band resilience against jamming, and runs a full STRIDE threat model. **Notably benchmarks a Raspberry Pi 4** as the CubeSat-representative software baseline (150ms ECDH startup, ~300µs/1kB AES-GCM block, exponential blow-up past ~84MB files) versus a Xilinx Zynq-7020 FPGA (80×/60× faster, <2% CPU, 0.037-0.085% of CubeSat power budget) — concrete, load-bearing numbers for anyone deciding software-only vs. hardware-accelerated crypto on a constrained platform. Validated against real UM5-Ribat CubeSat telemetry (launched Aug 16, 2024). `strong` — https://link.springer.com/article/10.1007/s10207-025-01184-z
- **"What is Cybersecurity in Space?"** (arXiv 2509.05496, AICCSA 2025) — maps **11 concrete research gaps** (secure routing for dynamic cross-links, onboard intrusion detection replacing hours-long ground-loop detection, DTN/blockchain-assisted recovery, post-quantum + QKD roadmapping since satellites launched now must stay secure to ~2040, lack of a shared "Space-CVE" list, zero-trust across 5G-NTN/drone/satellite hops, live service-impact KPIs during attacks, and the absence of open cyber-ranges). Directly cites the 2022 **KA-SAT/Viasat attack** as the field's watershed incident. `strong` — https://arxiv.org/html/2509.05496v1
- **Salim, Moustafa & Reisslein — "Cybersecurity of satellite communications systems: A comprehensive survey of the space, ground, and links segments"** (IEEE Communications Surveys & Tutorials, vol. 27, Feb 2025) — the most heavily cross-cited academic survey in this space right now; anchors nearly every 2025-2026 paper found in this search. `strong` (peer-reviewed, widely cited) — cross-confirmed via IEEE Xplore and multiple downstream citations.
- **NIST IR 8323r2 (draft) — "Foundational PNT Profile: Applying the Cybersecurity Framework..."** — NIST CSF profile specifically for GPS/PNT-dependent systems (jamming/spoofing resilience). `strong` (federal standard, initial public draft May 2026) — https://nvlpubs.nist.gov/nistpubs/ir/2026/NIST.IR.8323r2.ipd.pdf
- **CERT-In — "Cyber Security Framework and Guidelines for Space"** and **Cyber.gov.au — "Securing space"** — national-agency frameworks; useful for regulatory/compliance angles, largely restate NIST CSF + CCSDS guidance for their jurisdictions. `moderate` — https://www.cert-in.org.in/PDF/CyberSecurityFrameworkGuideline_for_space.pdf , https://www.cyber.gov.au/business-government/secure-design/securing-space
- **satellitetoday.com — "Three Years Post KA-SAT Attack, Viasat Exec Talks Lessons Learned"** (Jul 2025) — practitioner lessons-learned: incident-response *practice* (not just tooling) and tabletop exercises were the biggest gaps exposed, not crypto algorithm choice. `moderate` (trade press, named exec source) — https://www.satellitetoday.com/cybersecurity/2025/07/24/three-years-post-ka-sat-attack-viasat-exec-talks-lessons-learned-on-cybersecurity-posture/
- **UK gov.uk — "Cyber risks of cloud computing in the ground segment of the space sector"** — ground-segment-specific angle (increasingly cloud-hosted mission ops) that most satellite-security literature skips in favor of the space segment. `moderate` — https://www.gov.uk/government/publications/cyber-risks-of-cloud-computing-in-the-ground-segment-of-the-space-sector/cyber-risks-of-cloud-computing-in-the-ground-segment-of-the-space-sector

### Best-practice synthesis (what survived cross-checking across sources)

1. **Turn on SDLS / encrypt TM & TC by default.** CCSDS support for link-layer security is *optional* — the survey and NASA BPG both flag "encryption not enabled" as one of the most common real-world findings, not a theoretical risk.
2. **Never trust CFDP (or any legacy CCSDS app-layer protocol) unauthenticated.** Add AES-GCM + ECC-signed headers at the application layer if the mission still needs CFDP's file-transfer semantics; don't assume link-layer SDLS alone covers it.
3. **Defend against replay, not just eavesdropping.** GPS-disciplined time windows (or equivalent monotonic counters) for key/nonce validity are the recurring mitigation for CFDP/TT&C replay attacks.
4. **Space vehicle must be able to distrust its own ground segment.** NASA BPG's boundary-protection principle explicitly calls for the *space vehicle* to protect itself if the ground segment is compromised — not just the traditional "ground protects space" direction.
5. **Onboard anomaly detection, not ground-only monitoring.** Multiple sources (arXiv gaps paper, NASA BPG's Adversarial Actions Detection Function) converge on: ground-loop detection is too slow (hours) for an in-progress attack; lightweight onboard detection is the emerging norm for new missions.
6. **Budget crypto against real SWaP limits before choosing an architecture.** The Springer paper's Pi-4-vs-FPGA benchmark is the most concrete evidence available: software-only AES/ECC on a general-purpose ARM core is not viable much past small files/low duty-cycle; hardware acceleration (FPGA/ASIC crypto cores) is the practical answer for CubeSat-class power budgets.
7. **Plan crypto agility now for a post-quantum swap later.** Satellites launched today must remain secure into the 2040s; several sources (arXiv gaps paper, NIST) point at "harvest now, decrypt later" as a live, non-hypothetical risk against RSA/ECC-protected space links.
8. **Software/firmware integrity checks need a signed reference hash, not just a hash.** NASA BPG's malware-protection function is explicit: comparing against an unsigned "control" hash is defeatable by an attacker who can modify both the payload and the recorded hash together.

### Deep Dive — Does Standards/Academic Literature Address Execution-*Location* Attestation?

Space Fabric's central novelty claim is proving not just *what* ran but *where* (SEAP / "Proof of ET"). This round searched specifically for prior art on that WHERE-binding problem, independent of Space Fabric's own paper:

- **No CCSDS, NASA, or NIST standard addresses execution-location attestation.** A targeted search across CCSDS security Blue/Green Books, NASA SPARTA, and NIST SP 800-series found integrity and platform-identity attestation (WHAT), but nothing binding a proof to physical/orbital placement (WHERE) for satellites specifically. This is a negative/absence finding from a bounded search, not a formal literature-gap proof, but it corroborates Space Fabric's own stated gap. `moderate` (absence-of-evidence, bounded search).
- **The closest structural precedent is terrestrial, not orbital.** [IETF Internet-Draft `draft-lkspa-rats-verifiable-geo-fence-03`, "V-PEA" (Verifiable Proof of Environment Attestation)](https://datatracker.ietf.org/doc/html/draft-lkspa-rats-verifiable-geo-fence) (RATS working group, published 13 June 2026, expires 15 Dec 2026) — **independently fetched and verified real** — defines a TPM-sealed structure fusing platform integrity (WHAT) with physical residency within an approved geographic boundary (WHERE), explicitly for regulated/sovereign cloud/data-center deployments, with optional zero-knowledge proofs so the Attester doesn't have to disclose exact coordinates. This is the same WHAT+WHERE-fusion idea SEAP applies to satellites, but it is a data-center/geo-fencing draft, not a satellite-specific one — no orbital-mechanics-based verification (e.g., triangulation from Doppler/signal timing) and no ground-station-quorum consensus step. `strong`, independently verified via IETF datatracker.
- **On-orbit cryptographic key *generation*** (as opposed to key *rotation*, which is common) — no prior work found addressing this specifically; this appears to be a genuinely open point in the literature, corroborating rather than contradicting Space Fabric's framing of it as removing a pre-launch trust window / single-vendor dependency.
- **Independent 2026 satellite-TEE work exists but doesn't tackle location-binding.** [AegisSat: Securing AI-Enabled SoC FPGA Satellite Platforms](https://arxiv.org/abs/2602.19777) (Li, Novruzov, Singh, Wu, Rostami, Sadeghi — TU Darmstadt-affiliated; **independently fetched and verified real**, abstract matches) — secure boot + runtime isolation + authenticated in-orbit reconfiguration + rollback for AI-enabled SoC FPGA satellites — is a close sibling to Space Fabric's threat model (in-orbit update integrity) but targets FPGA reconfiguration integrity, not location/execution-site attestation. Treat as corroborating "satellite secure-boot-plus-runtime-integrity" is an active 2026 research area, not as prior art on SEAP's specific claim.
- **Byzantine-fault-tolerant ground-station quorums are not a novel primitive on their own** — independent 2026 work applies BFT consensus to LEO satellite constellations generally (not specifically to ground-station attestation quorums), meaning SEAP's quorum step borrows an established mechanism rather than inventing one; the novelty is applying it to attestation-evidence agreement specifically. This claim is single-scout-sourced and not independently re-fetched this round — flag for a follow-up check before treating it as settled.

## Deep Dive — Space Fabric as the Bridge Between Both Domains

This round's core finding: Raspberry Pi secure boot and satellite protocol security aren't just thematically similar (both papers/threads independently converged on "OTP-fused immutable root + signed chained stages" as good design) — [**Space Fabric: A Satellite-Enhanced Trusted Execution Architecture**](https://arxiv.org/abs/2603.23745) is a single system that needs both, on real flight-relevant hardware (USB Armory Mk II / i.MX6UL, the same board family used in actual CubeSat/nanosat prototyping):

1. **The boot-time root of trust is the i.MX6UL analog of Pi's BootROM+OTP scheme** (see Part A deep dive above) — HAB verifies GoTEE's Trusted OS image against an OTP-fused SRK hash, "establishing an immutable first link in the boot chain" (quoting the paper directly). This is the same immutable-hardware-root pattern this brief's Cross-Cutting Theme section already identified in Pi, just instantiated on different silicon with a richer multi-key/revocation model.
2. **Everything above that boot-time link is new protocol work, not reused from embedded secure boot** — the Attestation PTA (Protected/Pseudo Trusted Application) inside OP-TEE measures each loaded Trusted Applet, and SEAP (the paper's own contribution) adds the *satellite-specific* piece: proving physical/orbital location via a Byzantine-fault-tolerant ground-station quorum, something no CCSDS/NASA/NIST standard or terrestrial attestation draft (V-PEA above) currently does.
3. **One internal inconsistency worth flagging to a careful reader of the paper itself**, surfaced by close reading during this round: the paper's background section (~line 95) attributes the Trusted OS/Secure World to "Space Fabric's GoTEE Secure World," while its architecture section (~line 375) attributes the Attestation PTA specifically to "OP-TEE's Secure World." GoTEE's own README confirms it is a pure TamaGo/Go runtime-isolation framework with no attestation logic of its own — so either the paper is using "GoTEE" loosely to mean "the TrustZone Secure World substrate in general" (with OP-TEE as the actual TEE OS running inside it), or there's a genuine terminology drift between sections. Worth resolving before citing the paper's OP-TEE-vs-GoTEE claim precisely in any future write-up.
4. **Practical read:** if the goal is ever to prototype or critique Space Fabric's approach, the two domains this brief was tracking separately are actually the two halves of one system: Part A's embedded-secure-boot research (adapted to HAB/i.MX6UL) is exactly the boot-time foundation Space Fabric relies on and does not re-invent; Part B's satellite-protocol-security research (SDLS/CFDP/NASA BPG) is the layer SEAP is explicitly trying to extend with something those standards don't yet cover.

## Cross-Cutting Theme: One Chain-of-Trust Pattern, Two Domains

Both research threads converge on the same primitives:

- **Immutable root of trust** (Pi: masked BootROM public key / OTP fuse ↔ Satellite: NASA GSFC-STD-8012 bulk security standard + mission key material provisioned pre-launch, unpatchable in orbit).
- **Signed, chained stages** (Pi: EEPROM → BL3/U-Boot ↔ Satellite: SDLS-protected frames → authenticated CFDP application data).
- **Irrevocable lockdown decisions** (Pi: `revoke_devkey`/`program_jtag_lock` are one-way ↔ Satellite: once launched, there is no "re-flash the boot ROM" — both domains treat "ship with debug/JTAG-equivalent access open" as the top irreversible mistake).
- **"Signed" ≠ "safe."** UEFI's BlackLotus/LOGOFAIL/PIXIFAIL bootkits and CFDP's plaintext-by-default design are the same lesson from opposite ends: a cryptographic chain of trust only protects against *unauthorized* code, not *authorized-but-vulnerable* code or *unauthenticated* protocol data.
